# 커스텀 TP all-reduce — vLLM 실측 +32.9%

측정일 2026-10-21 · A/B = HP ZBook Ultra G1a (gfx1151, 128GB UMA) · USB4/TB 2케이블, tbv
모델 Qwen2.5-7B-Instruct, TP=2, external_launcher, eager(gfx1151 에서 torch.compile 불가)

전제: **TP 로 간다.** PP 는 단일 스트림 토큰 지연이 2배(연산 32ms → 64ms 직렬)라 t/s 가 안 나온다.
버블을 마이크로배치로 메우면 집계 처리량은 오르지만 요청당 t/s 는 그대로다.

|---:|---:|---:|---:|---:|

배치가 커질수록 이득이 커진다. 소형(56KiB)에서는 **고정비가 하드웨어 고유값(115 µs)** 이라
우리가 줄일 몫이 적고, 중대형에서는 NCCL 의 소프트웨어 오버헤드가 커지기 때문이다(reports/09 §1 #3·#4).

## 2. 정합성 — 비트 단위 정확

`step4/test_exact.py`. 두 랭크 입력을 시드로 결정하고 상대 입력을 로컬 재생성해 **정확한 정답**과 비교
(NCCL 을 기준으로 쓰지 않으므로 RCCL 패치/프로바이더 설정에 의존하지 않는다).

| dtype | 56 KiB | 229 KiB | 1 MiB | 최대절대차 |
|---|---|---|---|---|
| float32 | 일치 | 일치 | 일치 | 0.000e+00 |
| bfloat16 | 일치 | 일치 | 일치 | 0.000e+00 |
| float16 | 일치 | 일치 | 일치 | 0.000e+00 |

**우리 결과가 정답과 비트 동일**하다. vLLM 생성 텍스트의 해시가 NCCL 과 다른 것은
NCCL 의 환원이 정확한 합과 비트 동일하지 않기 때문이며, greedy 디코딩에서 토큰 하나가 뒤집히면
이후가 갈라진다. 생성 품질은 양쪽 모두 정상(앞 90자 동일, 문장 일관).

## 3. 결정적 발견 — NCCL 의 강점은 속도가 아니라 비동기성

NCCL 에 우리와 같은 기준(회당 스트림 동기)을 적용했더니 전체가 **138.5 → 113.5 tok/s** 로 떨어졌다.
측정 자체가 침습적이었고, 그게 사실을 드러낸다.

| 방식 | 56 KiB 회당 | tok/s (배치 8) |
|---|---:|---:|
| NCCL, 회당 동기 | 1057.5 µs | 113.5 |
| **자체, 회당 동기** | **255.3 µs** | **143.9** |
| NCCL, 고유 비동기 | (측정 불가 — 스트림 큐잉) | 138.5 |

→ **회당 4.1× 빠르지만 CPU 를 블록해 이점의 대부분을 돌려주고 있다.**

## 5. 설계 (step4/libtbvcoll.cpp)

호출자 포인터가 매번 바뀌므로 **사전등록 VRAM 바운스**로 복사한다(D2D 211 GB/s, 56KiB 0.27 µs →
고정비 115 µs 대비 무시 가능하고 MR 캐시 복잡도를 없앤다).

실측으로 확정한 결정:
1. **dmabuf MR 은 HSA export offset 으로 등록.** 버퍼마다 `hipMemGetHandleForAddressRange` 로
   export 하면 같은 슬랩 fd 가 나와 offset 0 두 MR 이 동일 메모리를 가리킨다(정합성 깨짐).
2. **호스트 flag 별도 WR 금지** — dmabuf 는 RAW_STREAM, 호스트는 일반 경로라 같은 QP·RC 라도
   순서 보장이 없다 → `WRITE_WITH_IMM` 의 recv 완료를 쓴다.
3. **선택적 시그널링(32 회당 1 회)** — 매 WR SIGNALED 는 임계경로에 +171 µs.
4. **레일 교차점 96 KiB** — 56KiB 는 1레일이 2레일보다 빠르다(133 vs 169 µs). 크기로 고른다.
5. **GPU 커널이 호스트 flag 를 올리는 완료통지는 쓸 수 없다.** 앞선 복사의 L2 더티라인이
   플러시되지 않아 NHI DMA 엔진이 오래된 데이터를 읽는다(실측 verify=BAD). 스트림 완료를
   그대로 쓰되 블로킹 대신 **바쁜-질의**로 스케줄러 슬립만 피했다(pre 45 → 37 µs).
6. **out-of-place** — vLLM 의 all-reduce 계약.

vLLM 훅: `GroupCoordinator.all_reduce` 를 가로채 TP 그룹만 보낸다. 지원 못 하는 경우
(cap 초과 / dtype / 비연속)는 NCCL 로 폴백한다(배치 8 에서 22344 회 중 폴백 114 회).

## 6. 다음 단계: 비동기화 (CPU 블로킹 제거)

`hipStreamWaitValue64` 가 gfx1151 에서 동작함을 확인했다(등록 OK, 스트림이 실제 대기,
플래그 해제 후 21.1 µs 에 진행). 설계:

```
메인(vLLM) 스레드:  k_copy → hipEventRecord → hipStreamWaitValue64(gflag_i, seq)
                    → k_acc → 즉시 반환 (CPU 블로킹 0)
진행 스레드:        이벤트 대기 → RDMA post → CQ 폴링 → gflag_i = seq (GPU 해제)
```
슬롯 K개 링이 필요하다(레이어 N+1 의 복사가 N 의 전송 중인 버퍼를 덮지 않게).
회수 예상: 스텝 55.8 - 47.5 = **8.3 ms** 중 런치갭 몫. **[추정]**

주의: TP 는 레이어 N+1 이 N 의 all-reduce 결과에 의존하므로 **한 마이크로배치 안에서는
통신과 연산이 겹치지 않는다.** 통신을 연산 아래로 숨기려면 독립 마이크로배치 2개가 필요하고,
vLLM 의 DBO 는 DeepEP all2all 백엔드를 요구해 dense 모델에선 쓸 수 없다
(→ local_analysis/VLLM_DBO_REQUIRES_DEEPEP_20261021.md).

## 8. 비동기 설계에 대한 경고 (2026-10-21 사고에서 배운 것)

`hipStreamWaitValue64` 로 멈춰 있는 스트림은 **GPU 사용률을 100% 로 표시한다.** 플래그를
스핀 폴링하기 때문이다. 실제 연산은 없지만 GPU 가 바쁜 것으로 보이고 CPU 도 100% 를 쓴다.

- 발견 경로: 프로브(`scratchpad/probe_waitvalue.cpp`) 첫 실행이 교착했다. 레거시 null 스트림의
  `hipMemcpy` 가 `hipStreamWaitValue64` 로 멈춘 스트림을 기다려 플래그가 영원히 올라가지 않았다.
  호스트의 `timeout` 은 **docker 클라이언트만** 죽이고 `--rm` 은 컨테이너 종료 시에만 발동하므로
  컨테이너가 44분간 살아 GPU 를 100% 로 물고 있었다.
- 비동기 설계에 주는 함의:
  1. 진행 스레드가 멈추면 GPU 가 영구히 스핀한다 → **플래그 대기에 타임아웃/워치독이 필요하다.**
  2. GPU 사용률 지표로는 "연산 중" 과 "플래그 대기 중" 을 구별할 수 없다 → 성능 측정 시
     사용률을 근거로 쓰지 말 것.
  3. 대기 중 스트림은 레거시 null 스트림 연산(`hipMemcpy`, `torch.cuda.synchronize()`)을
     교착시킬 수 있다. torch 스트림은 non-blocking 이라 보통 안전하지만 확인이 필요하다.
- 도구 수정: `step4/run_{armr,ar2,tbvcoll,exact}.sh` 에 `INNER_TO` 를 추가해 **컨테이너 안에서**
  `timeout` 으로 감쌌다. 호스트 timeout 만으로는 컨테이너 누수를 막을 수 없다.

## 12. 비동기 구현에서 실측으로 확정한 것

1. **플래그 해제는 피어 도착만으로 한다.** 내 송신 완료까지 임계경로에서 기다리면
   56 KiB 전송이 122 → 222 µs 로 악화된다. 송신 수거는 해제 뒤 `outstanding <= NSLOT-1` 로 미룬다
   (RC FIFO 완료 순서상 항목 i-NSLOT 의 송신 완료가 보장되어 슬롯 재사용이 안전하다).
2. **복사 완료통지는 복사와 같은 커널에서 해야 한다.** 블록마다 `__syncthreads()` 후 thread0 이
   `__threadfence_system()` → 도착 카운터 → 마지막 블록이 플래그. 별도 커널로 하면 앞선 복사의
   L2 더티라인이 플러시되지 않아 DMA 가 오래된 데이터를 읽는다(아침에 verify=BAD 로 확인).
   단, 이 방식(GPUSIG)이 성능 이득은 없었다(HIP 락 경합이 원인이 아니었음) — 기본값은 유지하되
   `TBV_GPUSIG=0` 으로 이벤트 방식도 쓸 수 있다.
3. **슬롯 4개가 최적.** 2~16 스윕에서 4 가 가장 좋고, 크면 캐시가 식어 전송이 25 µs 나빠진다.
4. **워치독 필수.** 오류 시에도 플래그를 올려야 GPU 가 영구 스핀하지 않는다(§8). 전 측정에서
   워치독 발동 0회.

| 448 KiB | 415.4 µs | 349 | 84% | 288.6 | 174 | 60% |
| 896 KiB | **698.5 µs** | 697 | **100%** | 466.1 | 349 | 75% |

**바이트당 전송은 완벽하다.** 손실은 전부 **레일 합산**에 있다.

### 15.2 두 레일은 공유 병목을 다툰다 (총합 ~1.82 GB/s 고정)

레일별 진행 스레드로 post 직렬화를 제거해 두 레일을 동시 출발시켰다(896 KiB, standalone):

| | rail0 도착 | rail1 도착 | max | 실효 대역 |
|---|---:|---:|---:|---:|
| 1스레드 (post 순차) | 435.4 | 500.2 | 500.2 | 1.834 GB/s |
| 레일별 스레드 | 505.8 | 458.6 | 505.8 | 1.814 GB/s |

rail1 이 41 µs 빨라진 만큼 rail0 이 70 µs 느려졌다. **총합은 보존된다** → 공유 자원 경합.
2레일 총합 상한 ≈ **1.82 GB/s = 와이어 2.63 GB/s 의 69%**.

벌크 벤치는 2레일로 2.445 GB/s(19.56 Gb/s, 93%)를 낸다. 차이는 **메시지마다 파이프라인을
새로 채운다**는 점이다. 113프레임 × 3.08 µs = 349 µs 의 와이어 시간에 메시지당 ~115 µs 의
NHI 파이프라인 채움이 더해지고, 이건 메시지 간 파이프라이닝으로만 상각되는데
**TP 의 레이어 의존성이 그걸 금지한다**(레이어 N+1 은 N 의 all-reduce 결과를 쓴다).

### 15.3 cap 크기 = 측정 아티팩트 (약 180 µs)

vLLM 의 `TBV_CAP` 기본 4 MiB × 슬롯 4 = 32 MB 영역에 896 KiB 메시지만 띄엄띄엄 쓴다.
cap 을 메시지 크기(917504)로 맞추자 전송 **926 → 650 µs**. 원래 인용한 730.8 µs 는 이 영향을 받았다.

### 15.4 vLLM 고유 CPU 경합 (약 130 µs)

| | rail0 post / 도착 | rail1 post / 도착 |
|---|---|---|
| standalone | 37.4 / 435.4 | 69.1 / 500.2 |
| vLLM (SYNC) | 55.8 / 585.8 | 103.1 / 664.0 |
| vLLM (ASYNC) | 59.9 / 592.5 | 112.8 / 683.4 |

post 는 드라이버의 프레임 분할 = CPU 작업인데 vLLM 에서 +18~34 µs 늘었다. 도착은 +150 µs.
아침에 인공 CPU 부하로 측정한 **+26%** 를 466 µs 에 적용하면 +121 µs 로 관측치와 맞는다.
진행 스레드 CPU 고정(`TBV_CPU=28`)은 post 를 조금 줄였으나 도착은 거의 못 바꿨다 →
남은 몫은 커널의 TX/RX softirq·NHI 인터럽트 경합이며 **IRQ affinity(sudo)** 가 필요하다.

활성 IRQ: **52·53 (rail0 = 0000:c5:00.5), 68·69 (rail1 = 0000:c5:00.6)**, 각 ~1,240만회,
현재 `smp_affinity_list = 0-31`(아무 코어).

# 20. 남은 격차의 원인 특정: IOMMU 변환 + GPU 메모리 트래픽

§19 의 IRQ affinity 를 적용하고(양 노드) 추적을 계속해 **원인을 특정했다.**

## 20.1 반증 추가 4건

| 가설 | 검증 | 결과 |
|---|---|---|
| IRQ affinity (52·53→28,29 / 68·69→30,31) | 양 노드 적용 후 측정 | **효과 없음**. post 는 60.5/66.4 → 48.1/48.6 (CPU 작업 −25%) 로 개선됐으나 **도착은 불변**. tok/s 1047.3 → 1044.8 |
| 바운스 버퍼가 vLLM 의 VRAM 선점 뒤 할당돼 GTT 로 밀림 | `--tbv-eager` 로 `LLM()` 전에 초기화 | **효과 없음** (+1.0%, 노이즈) |
| vLLM 의 CPU 부하 | standalone 에 인공 부하 14프로세스 | **반증, 오히려 빨라짐** (465 → 415 µs). 코어가 깨어 있어 C-state 진입이 없다 |
| NCCL 이 같은 tbv 장치에 QP 를 열고 proxy 가 폴링 | 폴백을 `sockettb` 로 돌려 NCCL 을 tbv 에서 분리 | **효과 없음** (623.2 → 605.5 µs) |

### 자기 측정 오류 정정
앞선 "연산 간격 스윕(200/560/1000 µs)" 은 **무효**였다. matmul 1회가 이미 3450 µs 여서
`_grep = max(1, round(gap/3450)) = 1` 이 되어 세 점 모두 같은 3450 µs 간격으로 돌았다.
그래서 447/465/472 µs 로 비슷하게 나온 것이다.

## 20.2 원인: 메모리 집약 트래픽이 DMA 를 느리게 한다

간격의 **성질**을 바꿔 재현했다(896 KiB, 2레일, standalone):

| 간격 종류 | 실제 간격 | 전송 |
|---|---:|---:|
| 없음 | 0 | **416.4 µs** |
| 연산 집약 (FP16 matmul) | 3450 µs | 481.1 µs |
| 메모리 집약 (64 MiB 읽기) | 628 µs | 434.4 µs |
| **메모리 집약 ×2** | 1248 µs | **582.1 µs** |
| vLLM 실측 | — | 623.2 µs |

**지속시간이 아니라 메모리 트래픽이 원인이다.** 연산 집약은 3450 µs 를 쉬어도 481 µs 인데
메모리 집약은 1248 µs 만으로 582 µs 가 된다. vLLM decode 는 스텝당 노드별 ~7 GB 를
~215 GB/s 로 읽으므로 이 조건에 정확히 해당한다.

## 20.3 기전: IOMMU 변환

```
/sys/class/iommu/ivhd0                      AMD-Vi 활성
0000:c5:00.5 → iommu_group 29, type=DMA-FQ   전체 변환(패스스루 아님)
0000:c5:00.6 → iommu_group 30, type=DMA-FQ
커널 cmdline: iommu 옵션 없음(기본값)
```

모든 DMA 접근이 IOMMU 페이지 테이블을 거친다. GPU 의 가중치 스트리밍이 **IOMMU TLB 를
밀어내고**, 이후 NHI DMA 의 주소 변환이 미스를 일으킨다. 전송 중 GPU 자체는
`hipStreamWaitValue64` 에서 멈춰 있는데도 전송이 느려지는 이유가 이것으로 설명된다
(트래픽이 *전송 중* 경합하는 게 아니라 *직전* 트래픽이 TLB 를 비워 놓는다).

## 20.4 검증 방법과 비용

런타임 변경은 불가하다 — 두 그룹의 장치가 `thunderbolt` 드라이버에 바인딩돼 있어
`/sys/kernel/iommu_groups/*/type` 쓰기가 드라이버 해제를 요구하고, 그러면 링크가 내려간다.

**커널 부팅 파라미터가 유일한 경로다(양 노드, 재부팅 필요):**
```
iommu.passthrough=1
```
기대 이득: 전송 623 → 최대 ~416 µs → 스텝당 약 12 ms → **배치 128 에서 약 +9%**. **[추정]**

**보안 트레이드오프를 먼저 판단해야 한다.** Thunderbolt/USB4 의 DMA 공격 보호는
바로 이 IOMMU 변환이 제공한다. 패스스루로 바꾸면 TB 포트에 꽂히는 장치가
시스템 메모리 전체에 접근할 수 있다. 두 노드를 직결 케이블로만 쓰는 닫힌 연구 환경이면
위험이 낮지만, 외부 TB 장치를 꽂는 용도로도 쓰는 노트북이라면 권하지 않는다.
대안(장치별 패스스루, DMA 버퍼 huge page)은 이 플랫폼에서 확인하지 못했다.

## 21. 최종 예산 (896 KiB, vLLM, 전송 623 µs) — 확정판

# 23. §20 의 IOMMU 기전 정정 — 패스스루는 답이 아니다

§20.3 에서 "GPU 의 가중치 스트리밍이 IOMMU TLB 를 밀어낸다" 고 썼는데 **틀렸다.** 확인 결과:

```
0000:c3:00.0 (GPU)  group=17  type=identity    ← GPU 는 IOMMU 변환을 거치지 않는다
0000:c5:00.5 (rail0) group=29  type=DMA-FQ
0000:c5:00.6 (rail1) group=30  type=DMA-FQ
domain0/domain1: security=user, iommu_dma_protection=1
```

GPU 가 identity 면 GPU 트래픽은 IOTLB 엔트리를 소비하지 않으므로 TB 장치의 변환을 축출할 수 없다.

남은 변형 가설은 "GPU 의 대용량 스윕이 **IOMMU 페이지 테이블을 캐시에서** 밀어내 이후 page walk 가
DRAM 까지 간다" 였고, 이건 cap 축소 이득(926→650 µs)과 일관됐다. **대리 시험으로 반증했다:**

| 슬롯 | DMA 발자국 | 4K 페이지 수 | tok/s | 전송 |
|---:|---:|---:|---:|---:|
| 8 | 14 MiB | 3584 | 1038.2 | 654.9 µs |
| 4 | 7 MiB | 1792 | 1063.5 | **605.0 µs** |
| 2 | 3.5 MiB | 896 | 1065.4 | 609.2 µs |

8→4 는 개선되지만 **4→2 는 포화**한다. page walk 가 병목이면 페이지를 또 절반으로 줄일 때
계속 개선돼야 한다. → **IOMMU 변환은 남은 격차의 원인이 아니다. `iommu.passthrough=1` 를 하지 말 것.**
(TB/USB4 의 DMA 공격 보호를 내주면서 얻을 것이 없다.)

## 23.1 런타임 변경 가능성 (질문에 대한 답)
기술적으로는 가능하다 — 그룹 내 모든 드라이버를 해제해야 type 쓰기가 받아들여진다:
```bash
echo 0000:c5:00.5 | sudo tee /sys/bus/pci/drivers/thunderbolt/unbind
echo 0000:c5:00.6 | sudo tee /sys/bus/pci/drivers/thunderbolt/unbind
echo identity | sudo tee /sys/kernel/iommu_groups/29/type
echo identity | sudo tee /sys/kernel/iommu_groups/30/type
echo 0000:c5:00.5 | sudo tee /sys/bus/pci/drivers/thunderbolt/bind
echo 0000:c5:00.6 | sudo tee /sys/bus/pci/drivers/thunderbolt/bind
```
하지만 **하지 말 것**: (1) unbind 가 domain0/domain1 과 TB 노드 12개, RDMA 장치를 모두 내린다
(자가복구는 검증됐지만 컨트롤러가 안 돌아오면 재부팅), (2) 위 대리 시험으로 이득이 없음이 확인됐고,
(3) `iommu_dma_protection` 이 1→0 이 된다. 부팅 파라미터가 런타임 unbind 보다 덜 위험하지만
어차피 할 이유가 없다.

## 23.2 남은 격차의 현재 최선 설명
APU 의 메모리 패브릭/캐시 일관성. UMA 에서 NHI DMA 가 GPU 가 캐시해 둔 메모리에 쓰려면
스눕/프로브가 필요하고, GPU L2 가 가중치로 가득하면 그 작업이 늘어난다. 메모리 집약 간격이
연산 집약보다 훨씬 나쁜 것(§20.2)과 일관된다. **플랫폼 특성이며 소프트웨어로 회수할 경로를
이 조사에서는 찾지 못했다.** [미해결]

# 24. 최종 확정 결과

양 노드 IRQ affinity 완전 적용(A: 52·53→28-29, 68·69→30-31 / **B 는 번호가 다름**: 53·54→28-29, 69·70→30-31).
